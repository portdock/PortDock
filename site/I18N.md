# 사이트 여러 언어 — 구조와 새 언어 붙이기

portdock.dev 는 한국어(`/`)·영어(`/en/`)가 모든 쪽을 갖고, **추가 언어**(ja·de·es·pt·pl·fr·vi·tr·it·id)는 «번역 범위» 의 쪽만 갖는다.
번역 범위 = **1차 묶음**(`SCOPE` 15쪽 — 모든 추가 언어 공통) + **2차 묶음**(`SCOPE2` 산업 웹 도구 10개)·**3차 묶음**(`SCOPE3` PC 하드웨어 테스트 웹 도구 10개)·**4차 묶음**(`SCOPE4` 통신 웹 도구 11개) 중 그 언어가 번역을 끝낸 쪽(`MORE[언어]` — 2차·3차·4차를 한 목록으로).
번역이 없는 쪽에는 그 언어 주소·hreflang·언어 고르기·sitemap 항목이 생기지 않고, 추가 언어 쪽에서 그런 쪽으로 가는 링크는 영어판으로 간다.

## 어디에 무엇이 있나

| 무엇 | 파일 |
|---|---|
| 언어 목록·이름·hreflang·og:locale, 주소 규칙 `url()` | `src/i18n/langs.ts` (`EXTRA_LANGS`) |
| 번역 범위 — 1차 `SCOPE`(공통), 2차 `SCOPE2`, 3차 `SCOPE3`, 4차 `SCOPE4`, 1차 밖 전부 `LATER`(= 2차 + 3차 + 4차), 언어별 목록 `MORE`, `pathsOf()`·`link()`·`langsOf()` | `src/i18n/scope.ts` |
| 일본어 사전 = **기준판** | `src/i18n/ja/` — `ui.ts` 공용 문구 · `common.ts` 프로그램·1차 웹 도구 이름 · `pages/*.ts` 쪽 글 · `lib/*.ts` 계산 라이브러리 문구 · `SafetyBody.astro`·`PrivacyBody.astro` 긴 본문 |
| 2차 묶음 사전 | `src/i18n/ja/batch2.ts` — 2차 도구 10개의 이름·소개(`webTools`), 쪽 글(`pages` → `pages/<쪽>.ts`), 문구 묶음(`lib` → `lib/<묶음>.ts`), 고장 원인 찾기 나무 글 `troubleshootTree.ts` |
| 3차 묶음 사전 | `src/i18n/ja/batch3.ts` — 3차 도구 10개의 이름·소개(`webTools`), 하드웨어 테스트 쪽 개인정보 줄(`hwPrivacy` → `components/HwPrivacy.astro`), 쪽 글(`pages` → `pages/<쪽>.ts`), 문구 묶음(`lib` → `lib/<묶음>.ts`) |
| 4차 묶음 사전 | `src/i18n/ja/batch4.ts` — 4차 도구 11개의 이름·소개(`webTools`), 쪽 글(`pages` → `pages/<쪽>.ts`), 문구 묶음(`lib` → `lib/<묶음>.ts`) |
| 사전 모음(빌드 때만 읽음) | `src/i18n/index.ts` (`DICTS` 1차 · `DICTS2` 2차 · `DICTS3` 3차 · `DICTS4` 4차 · `page2()`·`page3()`·`page4()`·`hwPrivacy()`) · 긴 본문은 `src/i18n/prose.ts` (`PROSE`) |
| 추가 언어 쪽 주소 만들기 | `src/pages/ja/[...path].astro`(`staticPaths("ja")`) → `src/i18n/LangPage.astro`(쪽 이름 → 화면) |
| 가이드·웹 도구 이름(링크 글, 번역 없는 쪽은 «(英語)» 표시) | `src/i18n/names.ts` (`pageName()`) |
| 한국어·영어 공용 문구 | `src/lib/i18n.ts` (`UI`), 쪽 글은 각 `views/*.astro` 의 `lang === "ko" ? {…} : lang === "en" ? {…} : dict(lang).pages.<쪽>` |
| 계산 라이브러리 문구 찾기 | `src/lib/tr.ts` — 한국어·영어는 코드 안 `msg(lang, ko, en)`, 추가 언어는 **영어 문장 → 번역** 표 |

계산 라이브러리 표의 열쇠는 코드의 영어 문장 그대로, `${…}` 자리만 `{}` 로 쓴다. 번역에서 `{0}` `{1}` … `{10}` `{11}` 로 그 값을 순서와 상관없이 쓴다.
끼워 넣은 값이 표에 그대로 있는 영어 문구(함수 이름·단위)면 그것도 번역된다. TXD·BI_DA+ 처럼 소문자 낱말이 없는 글은 그대로 둔다 — 다만 표에 **그 글 그대로** 있으면 옮긴다(`lib/tr.ts` 는 표를 먼저 본다). `Min ms`·`Qty`·`CS on`·`no ACK` 처럼 소문자 세 글자가 없는 짧은 머리글은 시험이 요구하지 않으므로 4차 묶음 사전에 직접 넣어 둔 것을 본뜬다.
쪽에는 그 쪽이 쓰는 묶음만 JSON 으로 실린다(`Base` 의 `libText`) — 한국어·영어 쪽의 JS 는 늘지 않는다.

## 새 언어 붙이는 순서 (예: 독일어 `de`)

1. **사전 복사** — `src/i18n/ja/` 폴더를 `src/i18n/de/` 로 통째로 복사하고 글을 옮긴다. 열쇠·배열 길이·함수 모양은 그대로(바꾸면 `astro check` 와 시험이 잡는다).
   - `ui.ts` → 공용 문구(머리줄·바닥글·내려받기·이용 안내·«이 페이지가 도움이 됐나요?»). `inEnglish`·`allToolsEn` 은 «(영어)» 같은 그 언어 표시.
   - `common.ts` → 프로그램 한 줄 소개 13개, 번역 범위 웹 도구 10개의 이름·소개, 도구 묶음 이름, «무엇을 하려나요?», 파일 크기.
   - `pages/*.ts` → 쪽마다 제목(`title`)·검색 제목(`seo`)·설명(`desc`)·본문. `home`·`download`·`privacy` 는 수를 받는 함수.
   - `lib/*.ts` → 계산·해석 결과 문구. 열쇠(영어)는 건드리지 말고 값만 옮긴다.
   - `SafetyBody.astro`·`PrivacyBody.astro` → 긴 본문(링크 포함 마크업). `const lang = "ja"` 를 `"de"` 로.
2. **등록 세 곳**
   - `src/i18n/langs.ts`: `EXTRA_LANGS` 에 `"de"`, `LANG_META` 에 `de: { name: "Deutsch", hreflang: "de", locale: "de-DE", og: "de_DE" }`.
   - `src/i18n/index.ts`: `import de from "./de/index.ts"` 하고 `DICTS` 에 `de`. `DICTS` 는 `Record<ExtraLang, Dict>`(`Dict` = 기준판 ja 의 모양)라 빠진 문구·다른 모양은 `astro check` 가 잡는다.
   - `src/i18n/prose.ts`: `de: { safety: DeSafety, privacy: DePrivacy }`.
3. **주소 파일** — `src/pages/ja/[...path].astro` 를 `src/pages/de/[...path].astro` 로 복사하고 `staticPaths("ja")`·`lang="ja"` 두 곳을 `"de"` 로(시험이 본다).
4. **검사** (모두 통과해야 함)
   - `npm run test -w portdock-site` — `src/lib/i18n.test.ts`: 사전 모양이 ja 와 같은지, 빈 문구, 번역 범위 도구의 영어 문장마다 번역이 있는지, 예시 입력을 돌렸을 때 영어가 남지 않는지, `pages/<언어>/` 와 `EXTRA_LANGS` 가 맞는지.
   - `npm run check -w portdock-site`, `npm run build -w portdock-site`
   - `node tools/site-check.mjs site/dist` — 언어별 제목(66칸)·설명(70~160칸, 한자·가나·한글은 2칸) 길이, hreflang 짝(서로 같은 묶음)·자기 언어 포함, 번역 범위 = 빌드된 `/<언어>/` 쪽 = sitemap 의 `/<언어>/` 주소, sitemap xhtml:link 가 있는 쪽만 가리키는지.
   - `node tools/privacy-check.mjs site/dist`
5. 빌드된 `site/dist/de/` 쪽을 몇 개 열어 남은 영어·한국어가 없는지 본다(문서 이름·규격 이름·제품 이름은 그대로 둔다).

새 언어는 위 1~5 로 1차 묶음만 붙이면 된다 — 2차·3차 묶음은 아래 순서로 따로(쪽 하나씩도 된다). 번역 전에는 그 언어에 그 묶음 쪽이 생기지 않는다.

## 2차 묶음 붙이는 법 (예: 독일어 `de` 에 웹 도구 10개)

2차 묶음 = `scope.ts` 의 `SCOPE2`: 배선도 만들기(wiring) · 고장 원인 찾기(troubleshoot) · 멀티미터 측정값 점검(multimeterCheck) · CAN 프레임 해석(canDecoder) · CAN 비트 타이밍(canTiming) · I2C(i2c) · UART 보율 오차(uartBaud) · Modbus RTU↔TCP(modbusRtuTcp) · XGT 해석(xgtDecoder) · 케이블 선정(cableSelection).
화면(`views/*.astro`)·계산 코드는 이미 세 갈래(`lang === "ko" ? … : lang === "en" ? … : page2(lang, "<쪽>")`)라 고칠 것이 없다 — 사전만 채운다.

1. **파일 복사** — 기준판 `src/i18n/ja/` 에서 아래를 `src/i18n/de/` 같은 자리로 복사해 옮긴다(열쇠·배열 길이·함수 모양 그대로, 영어판 쪽을 원천으로).
   - `batch2.ts` — `webTools`(도구 10개 이름·소개)와 `lib`·`pages` 를 모으는 파일. 아직 옮기지 않은 쪽은 `pages`·`webTools` 에서 빼도 된다(쪽 단위로 일부만 가능, `satisfies` 는 `Partial<…>` 로).
   - `pages/` 의 10개: `wiring.ts` `troubleshoot.ts` `multimeterCheck.ts` `canDecoder.ts` `canTiming.ts` `i2c.ts` `uartBaud.ts` `modbusRtuTcp.ts` `xgtDecoder.ts` `cableSelection.ts` — 쪽 제목(`title`·`seo` 66칸)·설명(`desc` 70~160칸)·본문·FAQ. `end`·`more`·`seeG` 처럼 링크 앞뒤로 나뉜 글은 그 언어 어순으로 앞·뒤 조각을 맞춘다.
   - `lib/` 의 12개: `wiring.ts` `troubleshoot.ts` `meterCheck.ts` `meterUi.ts` `canFrame.ts` `canTiming.ts` `i2c.ts` `uartBaud.ts` `modbusConvert.ts` `xgt.ts` `xgtManuals.ts` `cableSelect.ts` — **영어 문장 → 번역** 표(열쇠는 그대로, `{}` 자리는 `{0}` `{1}` …). 같은 영어 문장은 1차 묶음(`lib/*.ts`)과 같은 번역이어야 한다(시험이 본다).
   - `troubleshootTree.ts` — 고장 원인 찾기 질문 나무의 글. **노드 id 로 찾는 표**다(나무 모양·링크는 `data/troubleshoot.ts` 하나를 모든 언어가 함께 쓴다): `yes`·`no`, 증상 8개, 질문(`q`, 나무에 힌트가 있으면 `hint`, 예/아니오가 아닌 답만 `opts`), 결과(`title`·`causes`·`checks` — 나무와 같은 수·순서). `pages/troubleshoot.ts` 가 `tree` 로 가져온다.
2. **등록** — `src/i18n/index.ts`: `import de2 from "./de/batch2.ts"` 하고 `DICTS2` 에 `de: de2`.
3. **공개** — `src/i18n/scope.ts` 의 `MORE` 에 `de: SCOPE2_PATHS`(또는 옮긴 쪽 경로만 `["tools/i2c/", …]`; 3차까지 끝냈으면 `[...SCOPE2_PATHS, ...SCOPE3_PATHS]`). 이 한 줄로 `/de/tools/…` 주소·hreflang·언어 고르기·sitemap·도구 목록·홈의 «웹 도구 n개» 가 따라온다.
4. **검사** — 위 «새 언어» 4번과 같다. `npm run test -w portdock-site` 의 2차 묶음 시험이 `MORE.de` 의 쪽마다 본다: 쪽 글이 ja 와 같은 모양·빈 글 없음, 도구 이름, 나무 글 표가 나무와 맞음(`checkText()`), 화면·라이브러리의 영어 문장마다 번역, 브라우저 스크립트가 쓰는 문장이 그 쪽이 싣는 묶음(`libText`)에 있음, 예시 입력을 돌렸을 때 영어가 남지 않음.
5. 빌드된 `site/dist/de/tools/<도구>/` 를 열어 남은 영어·한국어를 본다(규격·문서 이름, 가이드 링크의 «(영어)» 표시, 언어 고르기의 «한국어» 는 그대로).

## 3차 묶음 붙이는 법 (예: 독일어 `de` 에 PC 하드웨어 테스트 10개)

3차 묶음 = `scope.ts` 의 `SCOPE3`: 마이크 테스트(micTest) · 키보드 테스트(keyboardTest) · 웹캠 테스트(webcamTest) · 스피커 좌우 테스트(speakerTest) · 마우스 더블클릭 테스트(mouseTest) · 게임패드 테스트(gamepadTest) · 모니터 불량화소·주사율 테스트(monitorTest) · 블루스크린 정지 코드 사전(bsodCodes) · 노트북 배터리 리포트 해석기(batteryReport) · 바코드 스캐너 테스트(barcodeTest).
구조는 2차 묶음과 같다 — 묶음마다 사전 파일(`batch3.ts`)·사전 모음(`DICTS3`)·쪽 글 찾기(`page3()`)가 따로고, 공개 목록 `MORE[언어]` 는 2차·3차를 한 목록으로 쓴다(`LATER` = 2차 + 3차). 화면(`views/*.astro`)·계산 코드는 이미 세 갈래라 고칠 것이 없다 — 사전만 채운다.

1. **파일 복사** — 기준판 `src/i18n/ja/` 에서 아래를 `src/i18n/de/` 같은 자리로 복사해 옮긴다(열쇠·배열 길이·함수 모양 그대로, 영어판 쪽을 원천으로).
   - `batch3.ts` — `webTools`(도구 10개 이름·소개), `hwPrivacy`(하드웨어 테스트 7쪽이 함께 쓰는 개인정보 두 줄 — `ads`·`tester` 는 링크 앞뒤 조각), `lib`·`pages` 를 모으는 파일. 아직 옮기지 않은 쪽은 빼도 된다(쪽 단위로 일부만 가능, `satisfies` 는 `Partial<…>` 로).
   - `pages/` 의 10개: `micTest.ts` `keyboardTest.ts` `webcamTest.ts` `speakerTest.ts` `mouseTest.ts` `gamepadTest.ts` `monitorTest.ts` `bsodCodes.ts` `batteryReport.ts` `barcodeTest.ts` — 제목(`title`·`seo` 66칸)·설명(`desc` 70~160칸)·화면 글·FAQ·화면 스크립트 문구(`err`·`msg`·`m` 묶음). 쪽마다 덧붙은 것: 웹캠 `resDefault`, 마우스 `wheel`(휠 4방향), 모니터 `screens`(전체 화면 색 10개), 키보드 `kbAria`. `more` 는 다른 웹 도구로 가는 링크의 앞·뒤 조각(링크 글은 `weave()` 가 끼운다 — 링크 수 + 1 조각).
   - `lib/` 의 6개: `hwSignal.ts`(스피커 채널·게임패드 버튼 이름) `inputTiming.ts`(마우스 버튼 이름) `keyboardLayout.ts`(화면 키보드 배열 이름) `bsod.ts`(정지 코드 39개의 뜻·원인 후보와 볼 순서 16개) `batteryReport.ts`(용량 변화 줄) `barcode.ts`(GS1 AI 이름·풀이) — **영어 문장 → 번역** 표(열쇠는 그대로). 같은 영어 문장은 1·2차 묶음과 같은 번역이어야 한다(시험이 본다 — 예: `Serial number` 는 MC 묶음과 같게).
2. **등록** — `src/i18n/index.ts`: `import de3 from "./de/batch3.ts"` 하고 `DICTS3` 에 `de: de3`.
3. **공개** — `src/i18n/scope.ts` 의 `MORE` 에서 그 언어 목록에 `...SCOPE3_PATHS`(또는 옮긴 쪽 경로만)를 더한다: `de: [...SCOPE2_PATHS, ...SCOPE3_PATHS]`.
4. **검사** — «새 언어» 4번과 같다. `npm run test -w portdock-site` 의 3차 묶음 시험이 `MORE.de` 의 3차 쪽마다 본다: 쪽 글이 ja 와 같은 모양·빈 글 없음, 도구 이름, `hwPrivacy`, 화면·라이브러리의 영어 문장마다 번역, 브라우저 스크립트가 쓰는 문장이 그 쪽의 `libText` 묶음에 있음, 정지 코드 39개·GS1 AI 전부·채널·버튼 이름을 돌렸을 때 영어가 남지 않음.
5. 빌드된 `site/dist/de/tools/<도구>/` 를 연다. 그대로 두는 것: 정지 코드 이름(DPC_WATCHDOG_VIOLATION)·파일 이름·명령(powercfg, sfc /scannow), 키 이름(Ctrl·Alt·Fn), 화면 키보드의 글자(배열이 영문·한국어뿐), 앱 이름(PortDock Port Inspector).

이 묶음에서 알아 둘 것(번역할 때 글에 맞게 적는다):
- **키보드 테스트의 화면 키보드는 한국어 106·영문 ANSI 104·ISO 105 세 배열뿐**(`lib/keyboardLayout.ts`). 일본어 JIS·독일어 QWERTZ·프랑스어 AZERTY 배열은 없다 — 키는 물리 위치(`KeyboardEvent.code`)로 켜지므로 그 자판에서도 같은 자리가 켜지지만, 글자는 미국식으로 보인다. 기본 배열은 브라우저 언어로 고른다(독일어·프랑스어 등 유럽 언어는 ISO, 그 밖은 ANSI). 배열을 더하는 것은 따로 할 일.
- **바코드 스캐너 테스트의 «깨진 글자 되살리기» 는 한국어 2벌식만.** 다른 언어 IME(일본어 かな 입력 등)로 깨진 글자는 되살리지 않는다 — 그 언어 글에서는 «스캔 전에 영문 입력으로» 를 안내한다.
- **배터리 리포트는 표 머리글이 아니라 표 모양으로 읽는다**(`lib/batteryReport.ts`) — 리포트 언어와 상관없다(일본어 머리글 시험 있음). 머리글 낱말(DESIGN·設計 …)은 순서가 헷갈릴 때만 쓴다.
- **블루스크린 사전의 코드 찾기는 «코드 (매개변수 4개)» 모양으로 찾는다**(이벤트 1001 문장 언어 무관). 화면 문구 «Stop code:» 의 그 나라 말(일본어 停止コード 등)은 `lib/bsod.ts` 의 `KEYWORD`·이름 앞 지우기 정규식에 더한다(시험도 한 줄).
- Windows 설정 경로·메뉴 이름(설정 → 개인 정보 및 보안 → 마이크, 이벤트 뷰어, 신뢰성 모니터 …)은 **그 나라 Windows 의 실제 표기**로 적는다.

## 4차 묶음 붙이는 법 (예: 독일어 `de` 에 통신 웹 도구 11개)

4차 묶음 = `scope.ts` 의 `SCOPE4`: ASCII 코드표(ascii) · HEX ↔ ASCII 변환기(hexAscii) · 정수·진수 변환기(integer) · Modbus 읽기 요청 묶기(modbusBlocks) · Modbus 연습장(modbusPractice) · MQTT 페이로드 디코더(mqttDecoder) · 산업 통신 pcap 해석기(pcapAnalyzer) · SPI 모드 도우미(spi) · UART 파형 그리기(uartWaveform) · 웹 시리얼 터미널(webSerial) · 로직 분석기 캡처 해석기(logicCapture).
구조는 2차·3차 묶음과 같다 — 사전 파일 `batch4.ts`·사전 모음 `DICTS4`·쪽 글 찾기 `page4()`, 공개 목록 `MORE[언어]` 는 2차·3차·4차를 한 목록으로 쓴다(`LATER` = 2차 + 3차 + 4차). 화면(`views/*.astro`)·계산 코드는 이미 세 갈래(`lang === "ko" ? … : lang === "en" ? … : page4(lang, "<쪽>")`)라 고칠 것이 없다 — 사전만 채운다.

1. **파일 복사** — 기준판 `src/i18n/ja/` 에서 아래를 `src/i18n/de/` 같은 자리로 복사해 옮긴다(열쇠·배열 길이·함수 모양 그대로, 영어판 쪽을 원천으로).
   - `batch4.ts` — `webTools`(도구 11개 이름·소개), `lib`·`pages` 를 모으는 파일. 아직 옮기지 않은 쪽은 빼도 된다(쪽 단위로 일부만 가능, `satisfies` 는 `Partial<…>` 로).
   - `pages/` 의 11개: `ascii.ts` `hexAscii.ts` `integer.ts` `modbusBlocks.ts` `modbusPractice.ts` `mqttDecoder.ts` `pcapAnalyzer.ts` `spi.ts` `uartWaveform.ts` `webSerial.ts` `logicCapture.ts` — 제목(`title`·`seo` 66칸)·설명(`desc` 70~160칸)·화면 글·FAQ. 쪽마다 덧붙은 것:
     - `ascii` 의 `names` — 제어 문자 32개·SP·DEL 의 그 언어 이름(약어가 열쇠, 표에 «그 언어 이름 — RFC 20 영어 이름» 으로 보이고 찾기 칸도 이 이름으로 찾는다). `count` 는 수를 받는 함수.
     - 수를 받는 함수: `modbusBlocks.tNote(요청 수, 바이트, 한 바퀴 시간)`, `pcapAnalyzer.sampleDl(KB)`, `logicCapture.dl(KB)`.
     - 링크 앞뒤 조각: `hexEnd`·`appEnd`·`asciiEnd`·`fEnd`·`end`·`ends`·`moreEnds` 는 링크 **뒤** 글(한국어·영어판은 «.»), `rtu`·`pcap` 은 `weave()` 조각(링크 수 + 1). 링크 글(다른 웹 도구 이름)은 사전에 두지 않는다 — 화면이 `pageName()` 으로 넣는다. `modbusBlocks.dLink`(장비 맵)는 번역 없는 쪽이라 화면이 «(영어)» 표시를 붙인다.
     - `mqttDecoder.m`·`webSerial.ev` — 화면 스크립트가 `data-msg` 로 받는 결과·로그 문구. `logicCapture.u` — 해석기 설정·파형·표 화면 글, `faq`·`refNotes`·`relNotes`·`sampleNotes` 는 줄 수 그대로.
   - `lib/` 의 10개: `ascii.ts` `intConv.ts` `modbusBlocks.ts` `modbusQuiz.ts`(문제·해설 문장 — 함수 이름·예외 뜻은 1차 `modbusDecode` 번역을 그대로 쓴다) `mqttDecode.ts`(패킷 칸 이름·CONNACK 응답 코드) `pcap.ts`(결과 표·알림·CSV 머리글) `spi.ts` `uartWave.ts` `webSerial.ts` `logic.ts`(해석 종류·값·오류·CSV 머리글) — **영어 문장 → 번역** 표(열쇠는 그대로). 같은 영어 문장은 1·2·3차 묶음과 같은 번역이어야 한다(시험이 본다 — 예: `function`·`Start`·`Address` 는 이미 앞 묶음에 있다).
2. **등록** — `src/i18n/index.ts`: `import de4 from "./de/batch4.ts"` 하고 `DICTS4` 에 `de: de4`.
3. **공개** — `src/i18n/scope.ts` 의 `MORE` 에서 그 언어 목록에 `...SCOPE4_PATHS`(또는 옮긴 쪽 경로만)를 더한다: `de: [...SCOPE2_PATHS, ...SCOPE3_PATHS, ...SCOPE4_PATHS]`. 이 한 줄로 1·2차 쪽(MC·Modbus 해석기, RTU↔TCP 변환기, 첫 화면·내려받기 쪽의 «무엇을 하려나요?»)에서 pcap 해석기·Modbus 연습장으로 가는 링크 글의 «(영어)» 표시도 저절로 빠진다(`pageName()`).
4. **검사** — «새 언어» 4번과 같다. `npm run test -w portdock-site` 의 4차 묶음 시험이 `MORE.de` 의 4차 쪽마다 본다: 쪽 글이 ja 와 같은 모양·빈 글 없음, 도구 이름, 화면·라이브러리의 영어 문장마다 번역, 브라우저 스크립트가 쓰는 문장이 그 쪽의 `libText` 묶음에 있음(화면 스크립트가 `documentElement.lang` 으로 언어를 고르지 않음), 정수 변환 오류·연습 문제 360개·MQTT 패킷·예시 pcap 캡처·CSV·웹 시리얼 설정 오류·로직 해석 글을 돌렸을 때 영어가 남지 않음.
5. 빌드된 `site/dist/de/tools/<도구>/` 를 연다. 그대로 두는 것: 근거 문서 이름(RFC 20, UM10204 …), 신호·필드 이름(SCK·MOSI·CPOL, MBAP, PUBLISH·QoS, Sparkplug 의 timestamp·seq·uuid), MQTT v5 이유 코드·속성 이름(규격 표기), 명령·파일 이름(pktmon etl2pcap, editcap -c, sample.pcapng), CSV 의 결과 값(ok·timeout …, 데이터라서).

이 묶음에서 알아 둘 것(번역할 때 글에 맞게 적는다):
- **pcap 해석기는 Web Worker 에서 푼다.** Worker 에는 쪽의 문구 표가 보이지 않으므로 화면이 `catalog` 로 넘기고 `lib/pcapWorker.ts` 가 등록한다 — 사전은 손댈 것 없다. 거래 표의 함수 이름·MC 명령·종료 코드는 1차 묶음(`modbusDecode`·`mc`)의 번역이 그대로 나온다(쪽이 그 묶음도 싣는다).
- 글 안의 메뉴 이름은 **그 나라 프로그램의 실제 표기**로(Wireshark «File → Export Specified Packets»·«Save As», Windows 장치 관리자 등). 일본어판 Wireshark 는 «ファイル → 指定したパケットをエクスポート».
- **Modbus 연습장 문제 문장은 `{}` 가 12개까지** 있다(«After slave {}, function 03 …»). `{10}` `{11}` 도 쓸 수 있다.
- ASCII 코드표의 128~255·한국어 글자 설명(`note`)은 그 언어의 문자 코드(일본어 Shift_JIS, 중·동유럽 Windows-1250 등)로 바꿔 적는다 — 영어판의 «CP949» 는 한국어 예다.
- 숫자 표시: pcap·로직 해석기의 수·시각은 브라우저가 그 언어 관례로 쓴다(`Intl.NumberFormat(lang)`). 사전의 글에서는 «1 000»·«1.000» 처럼 손으로 쓰지 않는다.

## 묶음을 더 더할 때

쪽을 번역 범위에 **더할** 때(5차 묶음 등)는 `scope.ts` 에 경로(공통이면 `SCOPE`, 언어별이면 새 `SCOPE5` 를 `LATER` 에 펼치고 `MORE`) + `index.ts` 의 `DICTS5`·`page5()` + 그 언어 사전의 쪽 글 + `LangPage.astro` 의 `VIEWS` 한 줄, 그리고 그 화면(`views/*.astro`)의 `ko ? A : B` 를 세 갈래로 바꾼다(`lang === "ko" ? A : lang === "en" ? B : page5(lang, "<쪽>")`). 시험은 `i18n.test.ts` 의 4차 묶음 시험 네 개(사전 모양·묶음끼리 같은 번역·쪽과 `libText`·예시 입력)를 본떠 더한다.
바꾼 뒤 한국어·영어 쪽 HTML 이 그대로인지 바꾸기 전 빌드와 비교한다(스크립트 묶음 이름·`data-lang` 만 달라야 한다).
화면 스크립트의 문구는 `data-*` 로 넘기거나 `msg(lang, ko, en)` 로 쓰고(`document.documentElement.lang === "ko"` 금지 — 언어는 폼의 `data-lang` 으로 받는다), 그 문구 묶음을 `Base` 의 `libText` 에 넣는다. 서버에서만 그리는 문구 묶음(`meterUi`·`xgtManuals`)은 `libText` 에 넣지 않는다(쪽 JSON 이 커지지 않게). 라이브러리의 `ko ? "…" : "…"` 는 `msg(lang, ko, en)`(또는 `t(ko, en)`)로 바꿔야 시험이 영어 문장을 찾는다.
다른 도구로 가는 링크 글은 사전에 박지 말고 `pageName()` 으로 — 앞 묶음 사전에 «(영어)» 를 붙여 박아 둔 링크 글이 있으면, 그 쪽이 번역됐을 때 `pageName()` 을 쓰도록 화면에서 바꾼다(4차 묶음 때 MC·Modbus 해석기의 pcap 링크, RTU↔TCP 변환기의 연습장 링크, `PickApp` 의 pcap 이름을 그렇게 바꿨다).

## 용어 원칙

- 그 나라 **제조사 공식 매뉴얼의 표기**를 따른다(일본어: 미쓰비시 전기 SLMP·MELSEC 매뉴얼, 옴론·키엔스 — 局番, ボーレート, パリティ, 終端抵抗, 保持レジスタ, サブヘッダ, 監視タイマ, 終了コード, デバイス点数, 一括読出し). 독일어는 DIN·NAMUR·Siemens 문서 표기 등.
- 같은 영어 문장은 모든 묶음에서 같은 번역(시험이 본다). 화면 이름(단추·칸)과 결과 문구의 용어를 맞춘다.
- 신호 이름(TXD·RTS·D0/D1)·함수 코드·규격 이름·제품 이름(PortDock Serial)은 옮기지 않는다.
- 문장은 그 언어로 자연스럽게 다시 쓴다(직역 금지). 검색 제목·설명은 그 나라 사람이 칠 검색어로.
- 번역이 없는 쪽으로 가는 링크 글에는 «(英語)» 처럼 그 언어로 «영어» 표시를 붙인다. 다른 웹 도구로 가는 링크 글은 사전에 박지 말고 `names.ts` 의 `pageName()`(문장 사이면 `weave()`)으로 만든다 — 번역 범위가 늘면 표시가 저절로 빠진다. `site-check` 가 번역된 쪽(`/<언어>/…`)으로 가는 링크 글에 표시가 남았는지 본다.
- 프로그램(앱) 화면은 한국어·영어·일본어(일본어는 0.11.0 부터, 도움말은 한국어·영어)뿐이라는 사실을 감추지 않는다. 다른 언어 앱 번역은 공개 전까지 적지 않는다.

## 하지 말 것

- **기계 번역을 그대로 싣지 않는다** — 구글 스팸 정책의 scaled content abuse 예에 «번역 같은 자동 변환» 이 있다. 기계 번역을 썼다면 용어·문장을 사람이 고친 뒤에.
- **번역 안 된 쪽에 그 언어 주소·hreflang 을 만들지 않는다** — 본문이 영어 그대로인 «다른 언어판» 은 중복으로 본다. `scope.ts` 밖의 쪽을 `pages/<언어>/` 에 따로 만들지 말 것(site-check 가 실패한다). 2차 묶음은 번역을 다 싣고 시험이 통과한 쪽만 `MORE` 에 넣는다.
- 한국어·영어 쪽의 주소·canonical·문구를 바꾸지 않는다. x-default 는 영어판, `llms.txt` 는 영어 그대로.
- 계산 코드(`lib/*.ts`)를 언어별로 복사하지 않는다 — 문구만 표로.
- 그림(`/img/…`)은 한국어·영어 두 벌뿐 — 추가 언어 쪽은 영어 그림을 쓰고 alt·설명만 옮긴다.
